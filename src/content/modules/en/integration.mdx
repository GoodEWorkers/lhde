## Integrating is not just plugging in

A technical flow can work perfectly while the project stays out of control. So the opening question
is not "how do we connect?" but: **when an application must receive hospital data, what actually has
to be decided?**

## ReEIF as a design checklist

You met ReEIF in module 1 as a **diagnostic** grid. Here it becomes a **design** grid: every layer
produces different decisions, risks and deliverables.

## What each layer must produce

| Layer | Expected deliverables |
| --- | --- |
| Infrastructure | Flow matrix, technical architecture file, authentication model, monitoring plan, operating procedure |
| Application | Exchange specification, expected version and profile, error and replay handling, test message sets |
| Information | Data dictionary, mapping tables, ValueSets, transformation rules, semantic regression tests |
| Business | Business scenarios, acceptance criteria, test sets, clinical validation, degraded-mode procedures |
| Organisation | Flow RACI, exchange contract, correction route, service commitment |
| Legal | Purpose analysis, legal basis, processing register, contractual clauses, traceability plan |

<Callout variant="key">
A good integration file makes **explicit the assumptions** that projects usually leave implicit. That
is its only value — and it is considerable.
</Callout>

<Reveal question="An SFTP interface works in pre-production. Can we call the integration project validated?">
No. Working in pre-production proves infrastructure and, partly, application. Four questions remain
open:

- **Information**: are codes and units aligned with the real production source?
- **Business**: has the process been replayed with the professionals involved, including in degraded
  mode?
- **Organisation**: who fixes an error found in production, and within what time?
- **Legal**: is the purpose you tested the one that is actually authorised?
</Reveal>

## Running case — integrating Argus

Goal: aggregate data from silos into a usable operational picture. Four domains to start: patient
identity (identifiers, status, matching, quality), appointments (schedule, cancellations, delays,
attendance), structure (services, units, beds, organisations, places), equipment (availability,
location, condition, maintenance).

Here ReEIF serves to verify that each source is **technically connected, syntactically usable,
semantically understood and organisationally governed**.

## Takeaway

A successful integration is an **alignment**. Technology, syntax, semantics, business, responsibility
and compliance must be thought through together.

ReEIF provides the map; the integration file documents the journey.

You now have the full toolkit. The final project asks you to use it: design, specify, then build an
interoperable prototype connected to a FHIR server.
