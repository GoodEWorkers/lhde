## The missing middle layer

A generic standard is **deliberately broad**: it has to cover many use cases. It defines a shared
vocabulary, structures and general mechanisms — FHIR `Patient`, `Observation`, `Encounter`.

In the field, that breadth becomes the problem: too many optional elements, several correct ways to
represent the same thing, open terminology choices. A profile **narrows the space of choices** for a
given context, so that the exchange becomes verifiable and reproducible.

<Callout variant="key">
Without profiling, "valid against the standard" does not mean "interoperable in my project".
</Callout>

## The IHE model — profiling a whole workflow

IHE does not reinvent standards: it **assembles existing standards to solve a use case**.

Examples still central to many hospital systems: **PDQ / PIX** for identity, **XDS** for document
sharing, **XUA / ATNA** for security and audit, **PAM** for movements, **SWF / RAD** for imaging
workflow.

## FHIR profiling — the StructureDefinition

A FHIR profile **is** a `StructureDefinition`. It is not a PDF: it is a **machine-readable** rule,
therefore executable and testable.

<CardGrid
  columns={3}
  cards={[

    { tag: 'Extensions', title: 'Adding what is missing', body: 'Adding a need absent from the base model without breaking compatibility.' },
    { tag: 'Invariants', title: 'Logical rules', body: 'Additional constraints expressed in FHIRPath, therefore automatically testable.' },
  ]}

```
Patient (FHIR Core)
  └── identifier  0..*        →  Patient-National
        └── identifier  1..*  (slice: national 1..1, local 0..*)
              └── system  1..1  fixed
              └── value   1..1
```

## Validating: from intention to evidence

A JSON or XML instance, a `StructureDefinition` profile, a terminology (`ValueSet`, `CodeSystem`) and
a validator: the output is a verdict — OK, warnings, errors.

<Reveal question="The validator reports '0 errors, 3 warnings'. Can you go live?">
It depends entirely on what the warnings say and what the profile covers. Three questions:

1. Do the warnings concern unmet **`extensible` bindings**? If so, has someone justified and
   documented the deviation?
2. Is the validated profile the **applicable** one (national or project), rather than FHIR Core?
3. Have the **business** scenarios been replayed? The validator says nothing about when the data
   arrives, or who acts on it.
</Reveal>

## Exercise — profile an appointment for Argus

Case: a hospital application must supervise flows of patients, rooms and resources.

| Question | To decide |
| --- | --- |
| Required data | Patient, appointment, service, place, equipment, status, priority, delay |
| Candidate resources | `Patient`, `Appointment`, `Schedule`, `Slot`, `Location`, `Organization`, `Device` |
| Profiling questions | Which mandatory elements? Which identifiers? Which status codes? Which extensions? |
| Expected proof | A valid JSON instance + the profile + the ValueSet + a validation test |

### Guided walkthrough — explore an existing profile

1. Open a FHIR implementation guide and pick one profile.
2. Note the canonical URL, the base resource and the maturity status.
3. Identify three constrained elements and their cardinalities.
4. Find one terminology binding and its binding strength.
5. Locate an example instance and explain why it conforms.
6. Describe how this profile would be validated in a real project.

Suggested profiles to start with: `Patient`, `Observation`, `DiagnosticReport`, `Appointment`.

## Takeaway

Profiling turns a standard into a **shared implementation language**.

- A generic standard leaves too much freedom to guarantee real interoperability.
- Profiles narrow the choices, make the rules explicit and enable validation.
- IHE profiles complete workflows with actors and transactions; FHIR profiles resources and exchange
  artefacts.
- An IG combines profiles, terminologies, examples, rules and tests.

So the right question is not "which standard?" but **"which profile for which use?"**.
