## The right question is not "which standard?"

It is: **what problem are we trying to standardise?** Each family of standards answers a different
kind of question. Treating them as competitors is the most expensive beginner mistake.

| Kind of question | Body / artefact |
| --- | --- |
| Who does what, when, with which transaction? | **IHE** |
| How do we structure and exchange the data? | **HL7** — FHIR, HL7 v2, CDA |
| How are images and related data encoded? | **DICOM** |
| How do we model clinical content durably? | **openEHR**, FHIR profiles |
| What does this code or observation mean? | **SNOMED CT, LOINC, UCUM** |
| How are study datasets analysed? | **CDISC, OMOP / OHDSI** |
| What is required locally? | **National agencies, HL7 Europe** |

<Callout variant="key">
Standards are not competitors by default: they often solve **different layers of the same system**.
Avoid the "one standard to rule them all" reflex.
</Callout>

## HL7 International — structure and exchange

The global standards development organisation for electronic health information exchange. Key
artefacts: FHIR, HL7 v2, CDA, CQL, implementation guides, profiles, extensions.

## IHE — making choices testable

IHE does not usually invent a base standard. It **profiles** existing standards for real-world
interoperability.

  caption="IHE makes implementation choices testable."

    { title: 'Profiles', body: 'A constrained use of HL7, DICOM, W3C and others.' },
    { title: 'Connectathon', body: 'Peer-to-peer implementation testing, under real conditions.' },
  ]}
/>

The usage logic: "we need document sharing / imaging access / patient identity management" → look for
an IHE profile.

| Profile | Need | Actors | Standards |
| --- | --- | --- | --- |
| PDQ / PIX | patient identity | Patient Consumer / Supplier | HL7 v2, IHE services |
| PAM | admission, encounter, movement | ADT source / consumer | HL7 v2 ADT |
| XDS.b | document sharing | Registry / Repository / Consumer | CDA, ebXML, SOAP |
| ATNA / XUA | audit, security, identity assertion | Secure node / user / app | TLS, SAML, audit trail |
| SWF / RAD | imaging workflow | Modalities, RIS, PACS | DICOM, HL7 v2 |

<Callout variant="warning">
"Legacy" does not mean obsolete. These profiles remain at the heart of very many hospital information
systems running today.
</Callout>

## DICOM — imaging and everything around it

The reference standard for medical imaging information and communication.

- **Objects**: images, series, studies, reports, waveforms, image-related metadata.
- **Services**: storage, query/retrieve, worklists, printing, structured reports, web access.
- **Conformance**: vendors declare which DICOM services and options their products support.

Three reflexes: DICOM for modalities, PACS and image objects; FHIR **around** DICOM for patient,
order, report and workflow integration; an IHE profile when you need a **tested** cross-system
imaging workflow.

## openEHR — modelling clinical content

openEHR separates the stable technical reference model from clinical content models.

<Reveal question="Engineer's question: are you designing a clinical data repository, an exchange API, or a common model for both?">
The answer decides the dominant standard. A longitudinal repository needing fine clinical queries
leans openEHR; opening up to an application ecosystem leans FHIR; needing both demands a **pivot
logical model** and explicit mappings — not an ideological arbitration.

## Activity — choosing the standards for Argus

Argus consumes: patient identity, appointments, structure, professionals, beds, equipment, logistics
and alerts. Goal: a shared operational picture for hospital coordination.

| Domain | Candidate answer |
| --- | --- |
| Patient identity | FHIR `Patient` / IHE PIXm, PDQm / national identity rules |
| Appointments | FHIR `Appointment`, `Schedule`, `Slot` + local workflow |
| Structure | FHIR `Organization`, `Location`, `HealthcareService` + governance |
| Professionals | FHIR `Practitioner`, `PractitionerRole` + national and internal identifiers |
| Equipment | FHIR `Device`, `DeviceMetric`; SDC for relevant devices |
| Imaging | DICOM + IHE imaging profiles + FHIR `ImagingStudy` / `DiagnosticReport` |
| Lab results | FHIR `Observation` / `DiagnosticReport` + LOINC + UCUM + SNOMED CT |
| Analytics | FHIR exports and mappings → OMOP; trials and submissions → CDISC |

<Callout variant="key">
There is rarely one answer. An architecture **combines** standards and **constrains** them through
profiles, governance and tests.
</Callout>

## Takeaway

- **HL7 / FHIR** structures exchange and APIs.
- **IHE** makes integration choices concrete and testable.
- **DICOM** dominates imaging interoperability.
- **SNOMED CT, LOINC, UCUM** make data meaningful.
- **CDISC and OMOP** organise research and analytics data.
- The **European and national layers** constrain global standards for real implementation.
