## A perfectly valid, perfectly incomprehensible message

```json
{ "code": "K", "value": 4.2, "unit": "?" }
```

Syntax says: the payload is valid and parsable. Semantics asks: do both systems understand the same
clinical concept? Safety asks: can a decision be made on this?

<Reveal question="List the questions these three fields leave open, before reading on.">
- Does `K` mean potassium — or something else in the sender's local registry?
- Which **specimen**: serum, plasma, urine?
- Which measurement **method**?
- Which **unit**: mmol/L, mEq/L?
- Which **reference range**, and for which population?

Five questions, no answers. And yet the message passes validation.
</Reveal>

<Callout variant="warning">
The most dangerous interoperability failures are **invisible**. Interoperability fails when meaning
is *assumed* instead of *specified*.
</Callout>

## From words to computable meaning

| Concept | System | Code |
| --- | --- | --- |
| Myocardial infarction | SNOMED CT | `22298006` |
| Serum potassium | LOINC | `2823-3` |
| millimole per litre | UCUM | `mmol/L` |

Three rules follow from that table:

- a code only means something **inside** a code system;
- the display text helps humans but **must not** be the source of truth;
- the same clinical concept can be represented in several terminologies depending on the use case.

### The main terminologies

| Terminology | Domain | Steward |
| --- | --- | --- |
| SNOMED CT | clinical findings, procedures, body structures | SNOMED International |
| LOINC | observations, laboratory tests, measurements, documents | Regenstrief Institute |
| UCUM | units of measure | Regenstrief / UCUM |
| ICD | disease classification and statistics | WHO |
| ATC | medicines classification | WHO Collaborating Centre |

<Callout variant="key">
No terminology covers everything. Semantic design is about **choosing the right one for the right
field** — and then documenting the choice.
</Callout>

### Binding: constraining meaning

A profile does not only constrain cardinalities: it can **bind** an element to a ValueSet. The
binding strength states how obligatory that is.

| Strength | Meaning |
| --- | --- |
| `required` | The code **must** come from the ValueSet. |
| `extensible` | Use the ValueSet if possible; otherwise justify. |
| `preferred` | Recommended but not mandatory. |
| `example` | Illustrative only. |

## The terminology server: meaning as a service

A terminology server is the central source of truth for code systems, value sets, mappings and their
versions. It lets applications validate, expand, inspect and translate codes **without hard-coding
terminology logic**.

It is essential to reproducibility: same code, same system, same version, same ValueSet context.

### The five operations to know

| Operation | The question it answers |
| --- | --- |
| `$expand` | Which codes does this ValueSet allow? |
| `$lookup` | What does this code mean, what are its properties? |
| `$validate-code` | Is this code valid in this context? |
| `$translate` | Which code in another system corresponds to it? |
| `$subsumes` | Is this concept broader, narrower, equivalent? |

<Callout variant="key">
Almost every terminology need reduces to one of those five questions: **list, inspect, validate,
translate, classify**.
</Callout>

## Mapping is not copying fields

A mapping declares how **meanings** relate. FHIR `ConceptMap` forces you to name that relationship.

| Relationship | Meaning | Example |
| --- | --- | --- |
| `equivalent` | same meaning | `PID-9.2` → `Patient.name.given` |
| `source-is-narrower-than-target` | source is more specific | precise timestamp → broader datetime |
| `source-is-broader-than-target` | source is less specific | general event time → precise field |
| `related-to` | related but not equivalent | "phone" field → `telecom` concept |
| `not-related-to` | explicit mismatch | multiple birth ≠ gender |

<Callout variant="warning">
Declaring `equivalent` by default is the most frequent and most expensive mistake. A wrongly named
relationship produces **silent** information loss.
</Callout>

## Logical models: protecting business meaning

Before choosing a FHIR resource, clarify the business concept.

**Business concept → logical model → FHIR profile** *(and, in parallel, → legacy format)*

- A logical model expresses functional requirements independently of FHIR or HL7 v2.
- It can act as a **pivot model** for mapping to several standards.
- It reduces the risk of letting one technical representation define the business meaning.

## Takeaway

Semantic interoperability makes health data **computable, comparable and safe to reuse**.

- Terminologies reduce ambiguity by assigning stable identifiers to concepts.
- FHIR connects structure to meaning through CodeSystem, ValueSet, ConceptMap and bindings.
- Terminology servers turn meaning into a service: expand, lookup, validate, translate, classify.
- Logical models protect business meaning before technical implementation.
