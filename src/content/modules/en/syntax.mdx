## Four questions we stack without noticing

Before asking what a message *means*, ask how it *travels* and how it is *structured*. These four
columns are independent, and confusing them is expensive.

## The five exchange patterns

| Pattern | Principle | Typical standard |
| --- | --- | --- |
| **Message push** | An event occurs, a message is sent | HL7 v2 ADT / ORU |
| **Document exchange** | A stable document is published or shared | CDA, PDF, national record |
| **Resource API** | A client reads, writes, searches resources | FHIR REST |
| **Event / subscription** | Systems react to changes | FHIR Subscription, broker |
| **Batch / file / ETL** | Data is exported, processed later | CSV, flat files, bulk export |

The choice depends as much on the business as on the technology. One at a time.

### 1 — Message push

A system sends a message when a business event occurs: admission, lab result, appointment creation.
The classic path is *source → integration engine → downstream applications*.

### 2 — Document exchange

A document is a **stable** clinical artefact: it can be signed, stored, shared and audited. Discharge
report, patient summary, prescription, referral letter.

Good for medico-legal trace, record sharing, cross-organisation continuity. Syntax options: PDF, CDA,
FHIR Document Bundle, national templates.

<Callout variant="warning">
A document can be **readable without being computable**. The right question is not "which format?"
but: is the expected use human reading, machine processing, or both?
</Callout>

### 3 — API / query / pull

The client asks for the data it needs, when it needs it.

```http
GET  /Patient?identifier=urn:oid:1.2.250.1.213.1.4.8|123456789
GET  /Observation?patient=123&code=http://loinc.org|2823-3
POST /Appointment
GET  /PractitionerRole?organization=Organization/42
```

Strengths: real-time access, search, modular reuse, an application ecosystem, mobile apps. Limits:
governance, authorisation, performance, versioning, and an explicit API contract — without which
every consumer reinvents its own assumptions.

### 4 — Events and subscriptions

Modern systems react to changes rather than polling repeatedly. Admissions and scheduling publish; a
mobile app and a command centre subscribe; a broker distributes.

Examples: appointment changed, new result available, bed status updated, device alert triggered.

### 5 — Batch, files and ETL

Not every exchange is real-time. Some cases tolerate delay or require large extracts: `source.csv`,
`patients.json`, `observations.ndjson`, `study.zip`, FHIR Bulk Data.

## Formats are not patterns

| Format | Typical shape | Can be used for |
| --- | --- | --- |
| HL7 v2 | pipe-delimited text | messages |
| CDA | XML document | clinical documents |
| FHIR | JSON / XML / RDF | API, document, message, bulk |
| DICOM | binary + metadata | imaging |
| CSV / NDJSON | flat / line-delimited | batch, analytics |

<Callout variant="key">
The same format can support several patterns. FHIR can be an API, a document, a message or a bulk
export. Saying "we do FHIR" therefore describes **no** architecture at all.
</Callout>

## Six questions to choose

<Reveal question="Before reading the list: which questions would you ask a business owner to decide between API and document?">
The six below cover the essentials. If you found three of them, you already have the architect
reflex.

1. Is the data needed **immediately**?
2. Does the receiver need the **full context** or only a notification?
3. Is the artefact **medico-legal** and stable over time?
4. Will the data be reused by **many** applications?
5. Is the exchange **operational** or **analytical**?
6. Who owns **correction**, **audit** and **reconciliation**?
</Reveal>

<Callout variant="key">
Syntax is an architectural choice, not just a developer preference.
</Callout>

## Argus, a deliberately multi-pattern case

Argus needs near-real-time data from several silos: patient identity, appointments, hospital
structure, resources, equipment, operational events.

There is no single "right" pattern. Identity and structure suit an API; appointments suit events;
history suits batch; documents stay documents. The control tower becomes possible once the patterns
are **explicitly selected and combined**.

## Takeaway

Syntactic interoperability is about **structuring and moving** data.

- Patterns matter: push, pull, document, event and batch solve different problems.
- Formats matter: HL7 v2, CDA, FHIR, DICOM, CSV/NDJSON each carry different assumptions.
- But syntax is not enough. The next module explains how **shared meaning** is manufactured.
