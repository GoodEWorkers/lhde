## La couche intermédiaire manquante

Un standard générique est **volontairement large** : il doit couvrir beaucoup de cas d’usage. Il
définit un vocabulaire commun, des structures et des mécanismes généraux — FHIR `Patient`,
`Observation`, `Encounter`.

Sur le terrain, cette largeur devient un problème : trop d’éléments optionnels, plusieurs façons
correctes de représenter la même chose, choix de terminologie ouverts. Un profil **réduit l’espace
des choix** pour un contexte donné, afin de rendre l’échange vérifiable et reproductible.

<Callout variant="key">
Sans profilage, « valide selon le standard » ne signifie pas « interopérable dans mon projet ».
</Callout>

## Le modèle IHE — profiler un workflow complet

IHE ne réinvente pas les standards : il **assemble des standards existants pour résoudre un cas
d’usage**.

<StepFlow
  caption="Un profil IHE spécifie un usage complet : pas seulement le format, mais le rôle de chaque système et les transactions attendues."
  steps={[
    { title: 'Cas d’usage', body: 'Quel problème concret ? Ex. retrouver un patient.' },
    { title: 'Acteurs', body: 'Quels systèmes jouent quel rôle ? Ex. Consumer / Supplier.' },
    { title: 'Transactions', body: 'Quels échanges entre acteurs ? Ex. requête / réponse.' },
    { title: 'Standards', body: 'Quels standards sous-jacents ? HL7 v2, CDA, DICOM, web services.' },
    { title: 'Profil testable', body: 'Un profil précis, documenté, éprouvé en Connectathon.' },
  ]}
/>

Exemples toujours au cœur de nombreux SIH : **PDQ / PIX** pour l’identité, **XDS** pour le partage
documentaire, **XUA / ATNA** pour la sécurité et l’audit, **PAM** pour les mouvements, **SWF / RAD**
pour le workflow imagerie.

## Le profilage FHIR — la StructureDefinition

Un profil FHIR **est** une `StructureDefinition`. Ce n’est pas une documentation PDF : c’est une
règle **lisible par une machine**, donc exécutable et testable.

<CardGrid
  columns={3}
  cards={[
    { tag: 'Cardinalité', title: 'Combien d’occurrences ?', body: '0..1, 1..1, 0..* — ce qui est obligatoire, ce qui est interdit, ce qui est répétable.' },
    { tag: 'Type', title: 'Quel datatype ?', body: 'Quels types et quelles références sont acceptés pour cet élément.' },
    { tag: 'Terminologie', title: 'Quels codes autorisés ?', body: 'Binding vers un ValueSet, avec une force donnée : required, extensible, preferred, example.' },
    { tag: 'Slicing', title: 'Découper une liste', body: 'Découper une liste répétable en « tranches » nommées — par exemple un identifiant national et un identifiant local.' },
    { tag: 'Extensions', title: 'Ajouter le manquant', body: 'Ajouter un besoin absent du modèle de base sans casser la compatibilité.' },
    { tag: 'Invariants', title: 'Règles logiques', body: 'Contraintes supplémentaires exprimées en FHIRPath, donc testables automatiquement.' },
  ]}
/>

```
Patient (FHIR Core)
  └── identifier  0..*        →  Patient-FR
        └── identifier  1..*  (slice : INS 1..1, local 0..*)
              └── system  1..1  fixé
              └── value   1..1
```

## Valider : passer de l’intention à la preuve

Une instance JSON ou XML, un profil `StructureDefinition`, une terminologie (`ValueSet`,
`CodeSystem`) et un validateur : le résultat est un verdict — OK, avertissements, erreurs.

<Reveal question="Le validateur affiche « 0 error, 3 warnings ». Peut-on mettre en production ?">
Cela dépend entièrement de ce que disent les avertissements et de ce que couvre le profil. Trois
questions à poser :

1. Les warnings portent-ils sur des **bindings `extensible`** non respectés ? Si oui, quelqu’un a-t-il
   justifié et documenté l’écart ?
2. Le profil validé est-il bien le **profil applicable** (national ou projet) et non FHIR Core ?
3. Les scénarios **métier** ont-ils été rejoués ? Le validateur ne dit rien du moment où la donnée
   arrive ni de qui agit.
</Reveal>

## Exercice — profiler un rendez-vous pour Argus

Cas : une application hospitalière doit superviser les flux de patients, de salles et de ressources.

| Question | À trancher |
| --- | --- |
| Données nécessaires | Patient, rendez-vous, service, lieu, ressource matérielle, statut, priorité, retard |
| Ressources candidates | `Patient`, `Appointment`, `Schedule`, `Slot`, `Location`, `Organization`, `Device` |
| Questions de profilage | Quels éléments obligatoires ? Quels identifiants ? Quels codes de statut ? Quelles extensions ? |
| Preuve attendue | Une instance JSON valide + le profil + le ValueSet + un test de validation |

### Parcours guidé — explorer un profil existant

1. Ouvrez un guide d’implémentation FHIR et choisissez un profil.
2. Relevez l’URL canonique, la ressource de base et le statut de maturité.
3. Identifiez trois éléments contraints et leurs cardinalités.
4. Trouvez un binding terminologique et sa force.
5. Localisez une instance d’exemple et expliquez pourquoi elle est conforme.
6. Décrivez comment ce profil serait validé dans un projet réel.

Profils suggérés pour démarrer : `Patient`, `Observation`, `DiagnosticReport`, `Appointment`.

## À retenir

Le profilage transforme un standard en **langage d’implémentation partagé**.

- Un standard générique laisse trop de liberté pour garantir l’interopérabilité réelle.
- Les profils réduisent les choix, rendent les règles explicites et permettent la validation.
- IHE profile des workflows complets avec acteurs et transactions ; FHIR profile les ressources et
  les artefacts d’échange.
- Un IG combine profils, terminologies, exemples, règles et tests.

La bonne question n’est donc pas « quel standard ? », mais **« quel profil pour quel usage ? »**.
