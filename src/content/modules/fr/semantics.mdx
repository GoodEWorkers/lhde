## Un message parfaitement valide, parfaitement incompréhensible

```json
{ "code": "K", "value": 4.2, "unit": "?" }
```

La syntaxe dit : la charge utile est valide et parsable. La sémantique demande : les deux systèmes
parlent-ils du même concept clinique ? La sécurité demande : peut-on décider sur cette base ?

<Reveal question="Listez les questions ouvertes par ces trois champs avant de continuer.">
- `K` désigne-t-il le potassium — ou autre chose dans le référentiel local de l’émetteur ?
- Quel **prélèvement** : sérum, plasma, urines ?
- Quelle **méthode** de mesure ?
- Quelle **unité** : mmol/L, mEq/L ?
- Quelles **valeurs de référence**, et pour quelle population ?

Cinq questions, aucune réponse. Et pourtant le message passe la validation.
</Reveal>

<Callout variant="warning">
Les défaillances d’interopérabilité les plus dangereuses sont **invisibles**. L’interopérabilité
échoue quand le sens est *supposé* au lieu d’être *spécifié*.
</Callout>

## De mots à sens calculable

| Concept | Système | Code |
| --- | --- | --- |
| Infarctus du myocarde | SNOMED CT | `22298006` |
| Potassium sérique | LOINC | `2823-3` |
| millimole par litre | UCUM | `mmol/L` |

Trois règles suivent de ce tableau :

- un code n’a de sens **qu’à l’intérieur** d’un système de codes ;
- le libellé d’affichage aide les humains mais **ne doit pas** être la source de vérité ;
- le même concept clinique peut se représenter dans plusieurs terminologies selon l’usage.

### Les grandes terminologies

| Terminologie | Domaine | Responsable |
| --- | --- | --- |
| SNOMED CT | constats cliniques, actes, structures corporelles | SNOMED International |
| LOINC | observations, examens de laboratoire, mesures, documents | Regenstrief Institute |
| UCUM | unités de mesure | Regenstrief / UCUM |
| ICD | classification des maladies et statistiques | OMS |
| ATC | classification des médicaments | Centre collaborateur OMS |

<Callout variant="key">
Aucune terminologie ne couvre tout. La conception sémantique consiste à **choisir la bonne
terminologie pour le bon champ** — puis à le documenter.
</Callout>

### Le binding : contraindre le sens

Un profil ne contraint pas seulement les cardinalités : il peut **lier** un élément à un ValueSet.
La force du binding indique le degré d’obligation.

| Force | Signification |
| --- | --- |
| `required` | Le code **doit** appartenir au ValueSet. |
| `extensible` | Utiliser le ValueSet si possible ; sinon, justifier. |
| `preferred` | ValueSet recommandé mais non obligatoire. |
| `example` | Illustration informative uniquement. |

## Le serveur de terminologie : le sens comme service

Un serveur de terminologie est la source de vérité centrale pour les systèmes de codes, les
ValueSets, les mappings et leurs versions. Il permet aux applications de valider, étendre, inspecter
et traduire des codes **sans coder en dur la logique terminologique**.

Il est indispensable à la reproductibilité : même code, même système, même version, même contexte de
ValueSet.

### Les cinq opérations à connaître

| Opération | Question à laquelle elle répond |
| --- | --- |
| `$expand` | Quels codes ce ValueSet autorise-t-il ? |
| `$lookup` | Que signifie ce code, quelles sont ses propriétés ? |
| `$validate-code` | Ce code est-il valide dans ce contexte ? |
| `$translate` | À quel code d’un autre système correspond-il ? |
| `$subsumes` | Ce concept est-il plus large, plus étroit, équivalent ? |

<Callout variant="key">
Presque tout besoin terminologique se ramène à l’une de ces cinq questions : **lister, inspecter,
valider, traduire, classer**.
</Callout>

## Mapper n’est pas copier des champs

Un mapping déclare comment des **significations** se relient. FHIR `ConceptMap` impose de nommer
cette relation.

| Relation | Sens | Exemple |
| --- | --- | --- |
| `equivalent` | même signification | `PID-9.2` → `Patient.name.given` |
| `source-is-narrower-than-target` | la source est plus spécifique | horodatage précis → date-heure plus large |
| `source-is-broader-than-target` | la source est moins spécifique | heure d’événement générale → champ précis |
| `related-to` | lié sans être équivalent | champ « téléphone » → concept `telecom` |
| `not-related-to` | incompatibilité explicite | naissance multiple ≠ sexe |

<Callout variant="warning">
Déclarer `equivalent` par défaut est l’erreur la plus fréquente et la plus coûteuse. Une relation
mal nommée produit une perte d’information **silencieuse**.
</Callout>

## Modèles logiques : protéger le sens métier

Avant de choisir une ressource FHIR, clarifiez le concept métier.

**Concept métier → modèle logique → profil FHIR** *(et, en parallèle, → format legacy)*

- Un modèle logique exprime des exigences fonctionnelles indépendamment de FHIR ou HL7 v2.
- Il peut servir de **modèle pivot** pour mapper vers plusieurs standards.
- Il réduit le risque de laisser une représentation technique définir le sens métier.

## À retenir

L’interopérabilité sémantique rend la donnée de santé **calculable, comparable et réutilisable sans
danger**.

- Les terminologies réduisent l’ambiguïté en attribuant des identifiants stables aux concepts.
- FHIR relie structure et sens via CodeSystem, ValueSet, ConceptMap et bindings.
- Les serveurs de terminologie transforment le sens en service : étendre, inspecter, valider,
  traduire, classer.
- Les modèles logiques protègent le sens métier avant l’implémentation technique.

Étape suivante : situer les standards et les organisations dans l’écosystème complet.
