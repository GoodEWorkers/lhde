## Quatre questions qu’on empile sans le savoir

Avant de demander ce qu’un message *veut dire*, demandez comment il *voyage* et comment il est
*structuré*. Ces quatre colonnes sont indépendantes, et les confondre coûte cher.

## Les cinq patterns d’échange

| Pattern | Principe | Standard typique |
| --- | --- | --- |
| **Message push** | Un événement survient, un message part | HL7 v2 ADT / ORU |
| **Échange documentaire** | Un document stable est publié ou partagé | CDA, PDF, DMP |
| **API de ressources** | Un client lit, écrit, recherche des ressources | FHIR REST |
| **Événement / abonnement** | Les systèmes réagissent aux changements | FHIR Subscription, broker |
| **Batch / fichier / ETL** | Les données sont exportées puis traitées plus tard | CSV, fichiers plats, bulk export |

Le choix dépend autant du métier que de la technique. Prenons-les un par un.

### 1 — Message push

Un système émet un message quand un événement métier survient : admission, résultat de biologie,
création de rendez-vous. Le chemin classique est *source → moteur d’intégration → applications
aval*.

### 2 — Échange documentaire

Un document est un artefact clinique **stable** : il peut être signé, stocké, partagé et audité.
Compte rendu, résumé patient, ordonnance, lettre de sortie.

Bon pour la trace médico-légale, le partage de dossier, la continuité inter-organisations. Syntaxes
possibles : PDF, CDA, FHIR Document Bundle, gabarits nationaux.

<Callout variant="warning">
Un document peut être **lisible sans être calculable**. La bonne question n’est pas « quel format ? »
mais : l’usage attendu est-il la lecture humaine, le traitement machine, ou les deux ?
</Callout>

### 3 — API / requête / pull

Le client demande la donnée dont il a besoin, au moment où il en a besoin.

```http
GET  /Patient?identifier=urn:oid:1.2.250.1.213.1.4.8|123456789
GET  /Observation?patient=123&code=http://loinc.org|2823-3
POST /Appointment
GET  /PractitionerRole?organization=Organization/42
```

Forces : accès temps réel, recherche, réutilisation modulaire, écosystème applicatif, applications
mobiles. Limites : gouvernance, autorisation, performance, versionnement, et un contrat d’API
explicite — sans quoi chaque consommateur réinvente ses hypothèses.

### 4 — Événements et abonnements

Les systèmes modernes réagissent aux changements plutôt que d’interroger en boucle. Admission et
planification publient ; application mobile et centre de commandement s’abonnent ; un broker
distribue.

Exemples : rendez-vous modifié, nouveau résultat disponible, statut de lit mis à jour, alerte
dispositif.

### 5 — Batch, fichiers et ETL

Tout échange n’est pas temps réel. Certains cas tolèrent le délai ou exigent de gros extraits :
`source.csv`, `patients.json`, `observations.ndjson`, `study.zip`, FHIR Bulk Data.

## Les formats ne sont pas des patterns

| Format | Forme typique | Peut servir à |
| --- | --- | --- |
| HL7 v2 | texte délimité par pipes | messages |
| CDA | document XML | documents cliniques |
| FHIR | JSON / XML / RDF | API, document, message, bulk |
| DICOM | binaire + métadonnées | imagerie |
| CSV / NDJSON | plat / ligne à ligne | batch, analytique |

<Callout variant="key">
Le même format peut soutenir plusieurs patterns. FHIR peut être une API, un document, un message ou
un export bulk. Dire « on fait du FHIR » ne décrit donc **aucune** architecture.
</Callout>

## Six questions pour choisir

<Reveal question="Avant de lire la liste : quelles questions poseriez-vous à un métier pour trancher entre API et document ?">
Les six qui suivent couvrent l’essentiel. Si vous en aviez trouvé trois, vous avez déjà le réflexe
d’architecte.

1. La donnée est-elle nécessaire **immédiatement** ?
2. Le récepteur a-t-il besoin du **contexte complet** ou d’une simple notification ?
3. L’artefact est-il **médico-légal** et stable dans le temps ?
4. La donnée sera-t-elle réutilisée par **plusieurs** applications ?
5. L’échange est-il **opérationnel** ou **analytique** ?
6. Qui possède la **correction**, l’**audit** et la **réconciliation** ?
</Reveal>

<Callout variant="key">
La syntaxe est un choix d’architecture, pas une préférence de développeur.
</Callout>

## Argus, un cas volontairement multi-pattern

Argus a besoin de données quasi temps réel issues de plusieurs silos : identité patient, rendez-vous,
structure hospitalière, ressources, matériel, événements opérationnels.

Le « bon » pattern n’est pas unique. L’identité et la structure se prêtent à l’API ; les rendez-vous
aux événements ; l’historique au batch ; les documents restent des documents. La tour de contrôle
devient possible quand les patterns sont **explicitement choisis et combinés**.

## À retenir

L’interopérabilité syntaxique consiste à **structurer et déplacer** la donnée.

- Les patterns comptent : push, pull, document, événement et batch ne résolvent pas le même problème.
- Les formats comptent : HL7 v2, CDA, FHIR, DICOM, CSV/NDJSON portent des hypothèses différentes.
- Mais la syntaxe ne suffit pas. Le module suivant explique comment le **sens partagé** se fabrique.
