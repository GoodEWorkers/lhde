## La bonne question n’est pas « quel standard ? »

Elle est : **quel problème essaie-t-on de standardiser ?** Chaque famille de standards répond à un
type de question différent. Les traiter comme des concurrents est l’erreur de débutant la plus
coûteuse.

| Type de question | Organisme / artefact |
| --- | --- |
| Qui fait quoi, quand, avec quelle transaction ? | **IHE** |
| Comment structurer et échanger la donnée ? | **HL7** — FHIR, HL7 v2, CDA |
| Comment encoder images et données associées ? | **DICOM** |
| Comment modéliser le contenu clinique durablement ? | **openEHR**, profils FHIR |
| Que signifie ce code ou cette observation ? | **SNOMED CT, LOINC, UCUM** |
| Comment analyser des jeux de données d’étude ? | **CDISC, OMOP / OHDSI** |
| Qu’est-ce qui est exigé localement ? | **ANS, Interop’Santé, HL7 Europe** |

<Callout variant="key">
Les standards ne sont pas concurrents par défaut : ils résolvent souvent des **couches différentes du
même système**. Évitez le réflexe « un standard pour les gouverner tous ».
</Callout>

## HL7 International — structurer et échanger

L’organisme mondial de standardisation pour l’échange électronique d’information de santé. Artefacts
clés : FHIR, HL7 v2, CDA, CQL, guides d’implémentation, profils, extensions.

## IHE — rendre les choix testables

IHE n’invente généralement pas de standard de base. Il **profile** des standards existants pour
l’interopérabilité du monde réel.

<StepFlow
  caption="IHE rend les choix d’implémentation testables."
  steps={[
    { title: 'Cas d’usage', body: 'Un problème clinique ou organisationnel concret.' },
    { title: 'Acteurs', body: 'Les systèmes qui endossent un rôle : Consumer, Supplier, Registry…' },

    { title: 'Profils', body: 'Un usage contraint de HL7, DICOM, W3C, etc.' },
    { title: 'Connectathon', body: 'Des tests d’implémentation pair à pair, en conditions réelles.' },
  ]}
/>

Logique d’usage : « nous avons besoin de partage documentaire / d’accès imagerie / de gestion
d’identité patient » → cherchez un profil IHE.

| Profil | Besoin | Acteurs | Standards |
| --- | --- | --- | --- |
| PDQ / PIX | identité patient | Patient Consumer / Supplier | HL7 v2, services IHE |
| PAM | admission, venue, mouvement | ADT source / consumer | HL7 v2 ADT |
| XDS.b | partage documentaire | Registry / Repository / Consumer | CDA, ebXML, SOAP |
| ATNA / XUA | audit, sécurité, assertion d’identité | Secure node / user / app | TLS, SAML, piste d’audit |
| SWF / RAD | workflow imagerie | Modalités, RIS, PACS | DICOM, HL7 v2 |

<Callout variant="warning">
« Legacy » ne veut pas dire obsolète. Ces profils restent au cœur de très nombreux SIH en production
aujourd’hui.
</Callout>

## DICOM — l’imagerie et ce qui l’entoure

Le standard de référence pour l’information et la communication en imagerie médicale.

- **Objets** : images, séries, études, comptes rendus, formes d’onde, métadonnées associées.
- **Services** : stockage, query/retrieve, worklists, impression, comptes rendus structurés, accès web.
- **Conformance** : les industriels déclarent quels services et options leurs produits supportent.

Trois réflexes : DICOM pour les modalités, PACS et objets image ; FHIR **autour** de DICOM pour
l’intégration patient, prescription, compte rendu, workflow ; un profil IHE quand il faut un workflow
imagerie **testé** entre systèmes.

## openEHR — modéliser le contenu clinique

openEHR sépare le modèle de référence technique stable des modèles de contenu clinique.

<Reveal question="Question d’ingénieur : concevez-vous un entrepôt clinique, une API d’échange, ou un modèle commun aux deux ?">
La réponse détermine le standard dominant. Un entrepôt longitudinal avec besoin de requêtes cliniques
fines penche vers openEHR ; une ouverture à un écosystème d’applications penche vers FHIR ; un besoin
des deux exige un **modèle logique pivot** et des mappings explicites — pas un arbitrage idéologique.
</Reveal>

## Activité — choisir les standards d’Argus

Argus consomme : identité patient, rendez-vous, structure, professionnels, lits, matériel, logistique
et alertes. Objectif : une vision opérationnelle partagée pour la coordination hospitalière.

| Domaine | Piste de réponse |
| --- | --- |
| Identité patient | FHIR `Patient` / IHE PIXm, PDQm / règles INS nationales |
| Rendez-vous | FHIR `Appointment`, `Schedule`, `Slot` + workflow local |
| Structure | FHIR `Organization`, `Location`, `HealthcareService` + gouvernance |
| Professionnels | FHIR `Practitioner`, `PractitionerRole` + RPPS / identifiants internes |
| Matériel | FHIR `Device`, `DeviceMetric` ; SDC pour les dispositifs concernés |
| Imagerie | DICOM + profils IHE imagerie + FHIR `ImagingStudy` / `DiagnosticReport` |
| Résultats de biologie | FHIR `Observation` / `DiagnosticReport` + LOINC + UCUM + SNOMED CT |
| Analytique | Exports et mappings FHIR → OMOP ; essais et soumissions → CDISC |

<Callout variant="key">
Il y a rarement une seule réponse. Une architecture **combine** les standards et les **contraint** par
des profils, de la gouvernance et des tests.
</Callout>

## À retenir

- **HL7 / FHIR** structure l’échange et les API.
- **IHE** rend les choix d’intégration concrets et testables.
- **DICOM** domine l’interopérabilité en imagerie.
- **SNOMED CT, LOINC, UCUM** donnent du sens à la donnée.
- **CDISC et OMOP** organisent la recherche et l’analytique.
- Les couches **européenne et française** contraignent les standards globaux pour une implémentation
  réelle.
