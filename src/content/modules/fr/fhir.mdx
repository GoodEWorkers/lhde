## Un détour utile : d’où vient le problème

L’informatique médicale est née comme un outil **administratif et légal** : répondre à des
obligations réglementaires, pas soutenir le soin. Les usages se sont ajoutés par croissance
organique, un besoin après l’autre — facturation, gestion des lits, bloc opératoire, imagerie,
biologie, urgences — chacun avec son logiciel, son périmètre et ses interfaces.

Résultat : un SI qui dérive en architecture spaghetti, une donnée produite *après coup* pour le
reporting plutôt que pour l’action, et des professionnels qui compensent manuellement la rupture
numérique.

<Callout variant="warning">
Le SIH comme **système de systèmes** reste largement un impensé. C’est ce vide conceptuel, plus que
la technique, qui explique l’état actuel.
</Callout>

Le numérique a basculé dans une nouvelle ère sans l’hôpital : web 2.0 et plateformes ouvertes,
explosion des smartphones et de l’IoT, big data et IA partout ailleurs. L’hôpital, lui, a choisi
l’homogénéisation plutôt que la standardisation. Le Covid a rendu la facture visible : échanges
laborieux, fichiers tableurs, ressaisies, aucune vue consolidée fiable sur les lits, les tests et les
flux patients.

FHIR a été la première réponse massive à l’échelle mondiale — la campagne de vaccination Covid en a
été le test grandeur nature.

### Lire une interaction FHIR

```http
GET /Appointment?date=ge2026-09-18&date=le2026-09-19&status=booked
     &_include=Appointment:location
     &_count=200
Accept: application/fhir+json
```

```json
{
  "resourceType": "Appointment",
  "id": "a-10432",
  "status": "booked",
  "serviceType": [{
    "coding": [{ "system": "http://snomed.info/sct", "code": "394914008", "display": "Radiology" }]
  }],
  "start": "2026-09-18T09:30:00+02:00",
  "end": "2026-09-18T09:50:00+02:00",
  "participant": [
    { "actor": { "reference": "Patient/8821" }, "status": "accepted" },
    { "actor": { "reference": "Location/salle-IRM-2" }, "status": "accepted" }
  ]
}
```

<Reveal question="Trois choses vous manquent encore pour savoir si cette ressource est exploitable par Argus. Lesquelles ?">
1. **Quel profil** contraint cette ressource ? `status`, `serviceType` et `participant` sont-ils
   obligatoires dans votre contexte ? (module Profilage)
2. **Quel ValueSet** est lié à `serviceType`, et avec quelle force de binding ? Sans cela, chaque
   silo enverra sa propre liste. (module Sémantique)
3. **Quelle provenance** : qui a produit cette instance, quand, à partir de quelle source, et qui la
   corrige si elle est fausse ? (module Architecture)
</Reveal>

## L’EHDS : l’interopérabilité devient une obligation

L’Espace Européen des Données de Santé est un règlement structurant, au périmètre très large : tous
les logiciels médicaux et médico-administratifs, tous les établissements, tous les acteurs de la
chaîne de soins — et le citoyen.

## À retenir

FHIR n’est pas « un format de plus ». C’est un **standard plateforme** : un modèle de données commun,
une API uniforme, une famille de paradigmes, et un écosystème d’outils — serveurs, validateurs, SDK,
guides d’implémentation.

Mais un standard générique laisse encore beaucoup trop de liberté pour garantir l’interopérabilité
réelle. Le module suivant traite de cette couche manquante : le **profilage**.
