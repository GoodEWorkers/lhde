## Intégrer, ce n’est pas seulement brancher

Un flux technique peut fonctionner tout en laissant le projet non maîtrisé. La question de départ
n’est donc pas « comment connecter ? » mais : **quand une application doit recevoir des données
hospitalières, que faut-il réellement décider ?**

## Ce que chaque couche doit produire

| Couche | Livrables attendus |
| --- | --- |
| Infrastructure | Matrice de flux, dossier d’architecture technique, modèle d’authentification, plan de supervision, procédure d’exploitation |
| Application | Spécification d’échange, version et profil attendus, gestion d’erreur et de rejeu, jeux de messages de test |
| Information | Dictionnaire de données, tables de mapping, ValueSets, règles de transformation, tests de non-régression sémantique |
| Métier | Scénarios métier, critères d’acceptation, jeux de tests, validation médicale, procédures de mode dégradé |
| Organisation | RACI du flux, contrat d’échange, circuit de correction, engagement de service |
| Juridique | Analyse de finalité, base légale, registre de traitement, clauses contractuelles, plan de traçabilité |

<Callout variant="key">
Un bon dossier d’intégration rend **explicites les hypothèses** que les projets laissent
habituellement implicites. C’est là son unique valeur — et elle est considérable.
</Callout>

<Reveal question="Une interface SFTP fonctionne en recette. Peut-on dire que le projet d’intégration est validé ?">
Non. Le fonctionnement en recette prouve l’infrastructure et, partiellement, l’application. Restent
ouvertes quatre questions :

- **Information** : les codes et unités sont-ils alignés avec la source réelle de production ?
- **Métier** : le processus a-t-il été rejoué avec les professionnels concernés, y compris en mode
  dégradé ?
- **Organisation** : qui corrige une erreur détectée en production, et sous quel délai ?
- **Juridique** : la finalité testée est-elle celle qui est autorisée ?
</Reveal>

## Cas fil rouge — intégrer Argus

Objectif : agréger des données issues de silos pour produire une vision opérationnelle exploitable.
Quatre domaines pour commencer : identité patient (identifiants, statut, rapprochement, qualité),
rendez-vous (agenda, annulations, retards, présence), structure (services, unités, lits,
organisations, lieux), matériel (disponibilité, localisation, état, maintenance).

Le ReEIF sert ici à vérifier que chaque source est **techniquement connectée, syntaxiquement
exploitable, sémantiquement comprise et organisationnellement gouvernée**.

## À retenir

Une intégration réussie est un **alignement**. Technique, syntaxe, sémantique, métier, responsabilités
et conformité doivent être pensés ensemble.

Le ReEIF fournit la carte ; le dossier d’intégration documente le trajet.

Vous avez maintenant l’outillage complet. Le projet final vous demande de l’utiliser : concevoir,
spécifier, puis réaliser un prototype interopérable connecté à un serveur FHIR.
